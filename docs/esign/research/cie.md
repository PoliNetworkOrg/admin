# CIE 3.0 signing agent research

Research date: 17 October 2026. Intended application: PoliNetwork's Windows, macOS and Linux local Go agent, with PDF preparation, CMS signed attributes and PAdES assembly on the backend.

## Findings that determine the implementation

Use the official middleware's PKCS#11 interface first, behind a small native worker process. Sign with `CKM_RSA_PKCS` and supply the 51-byte SHA-256 DigestInfo, then verify the returned RSA signature against the chosen certificate. Keep direct PC/SC as an experimental fallback until it passes a hardware matrix. On Apple Silicon, plan for an Intel worker if the installed middleware is Intel-only. The latest Mac App Store application and the older downloadable middleware are different distributions, with different paths.

Four distinctions matter:

- The CIE authentication key can produce a signature used in an Italian FEA workflow. It does not become a qualified signing key because the result is a PAdES PDF.
- The PKCS#11 certificate object is public after local pairing. The certificate on the card itself is protected by secure messaging and PIN verification.
- The middleware normally takes the last four PIN digits after pairing. The card protocol takes the full eight ASCII digits.
- `CKM_RSA_PKCS` receives DigestInfo and adds PKCS#1 v1.5 padding through the card. It does not hash the message. Passing only a 32-byte hash is insufficient for a standard SHA-256 RSA signature.

The evidence and exceptions follow. `UNVERIFIED` means the claim could not be established from the inspected sources or would require hardware/package testing. Source inspection is not a claim that the published binary has been tested. No CIE, reader, PIN attempt or installer execution was used in this research.

### A2. Pairing, certificate visibility and PIN contract

For the official PKCS#11 implementations on all three OSes, pair the card first with the local CIE application. Pairing uses the full eight PIN digits, reads the protected certificate and stores the first four digits for later use. Standard `C_Login(CKU_USER)` then accepts the last four digits. The code prepends the cached prefix. Passing eight digits to that path would build a twelve-digit credential. See [official first-use instructions](https://docs.italia.it/italia/cie/cie-middleware-windows-docs/it/master/primo-utilizzo-della-cie-con-il-middleware.html), [pairing/cache write:267–337](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/AbilitaCIE.cpp#L267-L337) and [login:363–440](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L363-L440).

After pairing, the certificate object is readable without `C_Login`. It is created with `CKA_PRIVATE=false`, `CKA_TOKEN=true`, X.509 type and `CKA_VALUE` holding DER. Session initialization decrypts the cache with help from the inserted card. An absent cache triggers a card-not-registered notification rather than a transparent physical-card certificate read. See [object creation:141–191](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L141-L191), [value:302–307](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L302-L307), [cache lookup:1271–1304](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L1271-L1304). Hardware confirmation of this public-object behavior is **UNVERIFIED** here.

Pairing is a host-side cache operation, not a permanent protocol prerequisite written to the card. The SDK/direct flow can instead authenticate with the full PIN and read the certificate. Pairing in the phone app does not establish the desktop computer's cache.

The pairing cache contains the certificate and first four PIN digits, not the citizen's private key, PUK or full PIN. `IAS::SetCache` AES-encrypts both before calling CacheLib. The AES key and IV are derived from SHA-512 of a card internal-authentication result, using a separate service key, reference `83`. Unix CacheLib adds another AES layer using embedded key material. Source comments warning about the demonstration cache do not mean the stored values are plaintext; IAS has already encrypted them.

There is a material macOS integration issue to test: `GetCardDir()` reconstructs the app-group path by taking the first four slash positions of `HOME`, apparently expecting a sandbox home. A normal unsandboxed Go process with `HOME=/Users/<user>` may resolve a different location. The path shown in the table is the intended application-context path, not proof that an arbitrary caller can load the module and find that cache. This remains **UNVERIFIED** on the latest package.

### A4. Mechanisms, labels, key size and errors

All three sources advertise signing mechanisms `CKM_RSA_PKCS`, `CKM_SHA1_RSA_PKCS`, `CKM_SHA256_RSA_PKCS`, and `CKM_MD5_RSA_PKCS`. They also advertise MD5, SHA-1 and SHA-256 digest mechanisms. RSA-PSS and `CKM_RSA_X_509` are not advertised. Do not infer support merely from constants in bundled PKCS#11 headers. See [Windows mechanism list:32–42](https://github.com/italia/cie-middleware/blob/8dd385e9b867c98fa099df689e427cfd6cb06d44/CSP/PKCS11/PKCS11Functions.cpp#L32-L42), [macOS:41–50](https://github.com/italia/cie-middleware-macos/blob/43da456fb3002e34beccda73b9bc4b149acae534/cie-pkcs11/PKCS11/PKCS11Functions.cpp#L41-L50), [Linux:43–52](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/PKCS11Functions.cpp#L43-L52).

A verified source defect makes `CKM_SHA256_RSA_PKCS` unsuitable as the integration default. `CDigestSHA256` identifies itself with `CKM_SHA_1` and returns the SHA-1 DigestInfo prefix. The digest-signing code concatenates that prefix with the 32-byte SHA-256 hash. This occurs in [Windows Mechanism.cpp:110–139](https://github.com/italia/cie-middleware/blob/8dd385e9b867c98fa099df689e427cfd6cb06d44/CSP/PKCS11/Mechanism.cpp#L110-L139), [macOS:116–145](https://github.com/italia/cie-middleware-macos/blob/43da456fb3002e34beccda73b9bc4b149acae534/cie-pkcs11/PKCS11/Mechanism.cpp#L116-L145) and [Linux:116–145](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/Mechanism.cpp#L116-L145). Actual distributed-binary behavior is **UNVERIFIED**. Use `CKM_RSA_PKCS` with the explicit SHA-256 DigestInfo described in B5 and independently verify the result. Even a correct standard `CKM_SHA256_RSA_PKCS` would expect the original message bytes, not an already computed digest.

The module reports a 1024–2048-bit mechanism range, while deriving actual key material from the certificate. The original CIE profile's citizen key is RSA-2048. Object label and ID are the four bytes `CIE0` for the certificate and both keys. Token template name is `CIE`. Slot description comes from the PC/SC reader name. The token label code uses NUL filling and attempts to append a serial after an embedded NUL; serial population is partly disabled in the inspected version. Exact rendered token labels are therefore **UNVERIFIED**, and should not be selection criteria. See [mechanism range:1091–1110](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/PKCS11Functions.cpp#L1091-L1110), [object attributes:140–188](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L140-L188), [token name:57](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CardTemplate.cpp#L57), [Slot.cpp:365–447](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/Slot.cpp#L365-L447).

`C_Login` maps user-PIN status `6983` to `CKR_PIN_LOCKED`, value `0xA4`; `63C0`–`63CF`, `6700` and `6300` to `CKR_PIN_INCORRECT`, value `0xA0`. Linux/macOS use the numeric attempts count in platform notifications; the standard return code does not carry it, and Windows leaves the numeric-count assignment commented out. Token flags are static and do not provide dynamic `CKF_USER_PIN_COUNT_LOW`/`FINAL_TRY` state in this implementation. `CKU_SO` uses PUK. Windows maps blocked PUK to `CKR_PIN_LOCKED`; Linux/macOS put that mapping inside the user-PIN branch, so their standard login path can instead throw a generic card error for blocked PUK. The sign path re-authenticates and collapses any PIN-verification failure to `CKR_PIN_INCORRECT`. Do not promise exact retry counts or reliable blocked-PUK diagnosis through PKCS#11. The Windows blocked-PUK branch is explicit in [Windows CIEP11Template.cpp:299–326](https://github.com/italia/cie-middleware/blob/8dd385e9b867c98fa099df689e427cfd6cb06d44/CSP/PKCS11/CIEP11Template.cpp#L299-L326). See [login/flags:359–435](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L359-L435), [sign:449–473](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L449-L473). The supplied suffix is retained encrypted in process memory for the session and cleared by logout.

### A5. Official signing SDK, extensions and CLI

The repositories contain real `cie_sign_sdk` and `Sign/CIESign.*` code. Linux builds the SDK as a static library, then links it into the middleware. The available source trees include substantial PDF, XML and cryptographic dependencies; embedding the whole SDK would bring those into the agent distribution. This is useful programmatic source, but a separately versioned, supported `libcie-sign` shared-library product or digest-signing CLI was not found. Installed CLI availability is **UNVERIFIED**; source examples such as Windows `EsempioPKCS11` and `TestCIE` are not a documented production CLI. See [Linux build instructions](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/README.md#L35-L45), [SDK CMake:124,151–152](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie_sign_sdk/CMakeLists.txt#L124-L152).

A middleware extension signs whole files:

```c
CK_RV firmaConCIE(const char *inFilePath, const char *type,
    const char *pin, const char *pan, int page,
    float x, float y, float w, float h, const char *imagePathFile,
    const char *outFilePath, PROGRESS_CALLBACK progress,
    SIGN_COMPLETED_CALLBACK completed);
```

Windows uses `__stdcall`; Linux/macOS expose the corresponding native C entry point. `type="pdf"` selects PDF signing, while other paths produce CAdES. Inputs include a paired-card PIN suffix and PAN; the implementation rebuilds the full PIN. It then handles PDF/CMS output locally, so it exceeds the chosen agent responsibilities. The ABI and callbacks must be taken from the exact version's headers. See [FirmaConCIE.cpp:24–29,112–140](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/FirmaConCIE.cpp#L24-L140).

The lower C SDK follows `disigon_sign_init()` → `disigon_sign_set(ctx, option, value)` → `disigon_sign_sign(ctx)` → `disigon_sign_cleanup(ctx)`. Options include IAS instance, PIN, filenames, CAdES and PDF subfilter/appearance. See [CIESign.cpp:25–142](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/Sign/CIESign.cpp#L25-L142), [public SDK header](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie_sign_sdk/include/disigonsdk.h).

The C++ `CCIESigner(IAS*)` has `Init(const char *fullPIN)`, `GetCertificate(alias, CCertificate**, id)`, `Sign(data, id, algo, signature)` and `Close()`. `Init` performs DH/DAPP/PIN itself. Here `Sign` with `algo=CKM_SHA256_RSA_PKCS` treats `data` as an already computed digest and builds DigestInfo; `CKM_RSA_PKCS` passes supplied DigestInfo unchanged. That internal SDK convention differs from standard PKCS#11. It needs a configured IAS/transport instance and is not a clean, stable Go C ABI. See [CIESigner.h](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie_sign_sdk/include/CIESigner.h), [implementation:37–154](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie_sign_sdk/src/CIESigner.cpp#L37-L154).

## B. Direct CIE card protocol

### B1. Contactless access, application selection and files

CIE 3.0 communicates exclusively over ISO 14443 contactless. It has separate MRTD/ICAO and IAS applications. A PC/SC connection over an NFC reader is a host API, not a contact interface on the card. PACE, BAC and ICAO Chip Authentication discussed for passport data do not precede the middleware's IAS signing sequence. The IAS flow uses its own DH exchange and Device Authentication with Privacy Protection, called DAPP in the code, then PIN verification. There is no CAN or MRZ input in that sequence. This last statement is a source-trace conclusion, not a promise about unrelated CIE applications. See the chip specification §§2–6 and the actual [login sequence, `CIEP11Template.cpp:378–435`](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L378-L435).

The code contains two AIDs:

The current [ATR table:7–19](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/ATR.cpp#L7-L19) includes Gemalto, STM, NXP, Actalis 2023/B946 and Bit4id 2023/B9547. The reference matcher sorts bytes and tests set inclusion at lines 22–55, rather than matching an ordered ATR prefix. That implementation should not be copied as a reliable parser.

The file map is established by [IAS.cpp:74–115,390–419](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L74-L115) and Annex A of the chip specification:

| Context  | EF               | Purpose                                                                   | Access before PIN                       |
| -------- | ---------------- | ------------------------------------------------------------------------- | --------------------------------------- |
| IAS/root | `D003`           | `EF.SN.ICC`, PAN/card chip identifier, used to locate cache entries       | Public                                  |

Read each EF with `00 A4 02 04 02 <FID-hi> <FID-lo>`, followed by `00 B0 <offset-hi> <offset-lo> 80` in 128-byte chunks. For `6Cxx`, retry the same READ BINARY with `Le=xx`. Append data returned with `6282` and stop. `6B00` also terminates the reference read loop. The same logical commands are wrapped in SM once active. Trim a certificate to its ASN.1 encoded length rather than treating trailing file storage as part of DER. See [readfile/readfile_SM:197–279](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L197-L279), [certificate parsing:300–303](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L300-L303).

A direct implementation therefore cannot offer a first-use certificate read without the user's full PIN. Its `GetCertificate` step must open an authenticated session, or explicitly include PIN acquisition, rather than assuming the two-operation interface means an unauthenticated read. The official desktop library avoids that prompt by returning an encrypted local certificate cache populated during pairing.

### B2. Establish the DH secure channel

The following describes the source's logical APDUs. `Lc` is the actual encoded data length. The transport may split long data into chained commands.

1. Connect through PC/SC, acquire a card transaction and reset/reselect as needed. Select IAS, read PAN, select the CIE DF, read `1004`. Obtain DH parameters and the external-authentication key metadata before beginning SM. The actual setup is in [AbilitaCIE.cpp:440–471](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/AbilitaCIE.cpp#L440-L471).
2. `InitDHParam` uses GET DATA `00 CB 3F FF`. Gemalto sends data `4D 08 70 06 BF A1 01 02 A3 80` and parses returned `g,p,q`. Other supported families make three GET DATA calls with `4D 0A 70 08 BF A1 01 04 A3 02 97 00`, then the same bytes with tag `98` and `99`. These request `g`, `p` and `q`. The public EF.DH is also read during pairing for SOD verification. Do not confuse that file read with the GET DATA route used to initialize live key agreement. [IAS.cpp:1031–1073](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L1031-L1073).
3. Obtain root CV/external-authentication metadata with `00 CB 3F FF`, data `4D 09 70 07 BF A0 04 03 7F 49 80`. Parse modulus tag `81`, public exponent `82`, CHR `5F20`, CHA `5F4C`. The code uses the shared external-authentication private exponent from `ExtAuthKey.cpp`. `CA_CAR=CHR[4:]`, `CA_AID=CHA[:6]`. [IAS.cpp:1087–1106](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L1087-L1106).
4. Generate terminal DH private exponent `x`; calculate `Y_IFD=g^x mod p`. Send MSE:Set KAT `00 22 41 A6`, data `80 01 9B || 83 01 81 || TLV(91,Y_IFD)`. Read `Y_ICC` with `00 CB 3F FF`, data `4D 04 A6 02 91 00`. Parse the response's nested ASN.1 content. Calculate `ZZ=Y_ICC^x mod p`. [IAS.cpp:574–617](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L574-L617).
5. Derive `Kenc=SHA256(ZZ || 00 00 00 01)[:16]` and `Kmac=SHA256(ZZ || 00 00 00 02)[:16]`. Initialize the eight-byte send sequence counter to `00 00 00 00 00 00 00 01`. SM is now active and covers DAPP itself. [IAS.cpp:621–636](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L621-L636).

These are finite-field DH values, not ECDH. Obtain the domain parameters from the card instead of inventing constants. The original chip specification describes 256-byte IAS DH/key objects. Domain validation and public-key subgroup validation in a new implementation need an explicit design; their presence in a robust Go implementation must not be inferred from the reference's minimal checks. The reference draws a `q`-sized random exponent, compares only its first byte to the first byte of `q`, and forces an odd low bit. That is what the source does, not a recommended exponent-sampling specification.

An interoperability trap remains **UNVERIFIED** on hardware: Linux's modular-exponentiation helper uses `MinEncodedSize()` and special-cases a 255-byte result to 256 bytes. Do not silently substitute an arbitrary big-integer serialization in a Go port. Test leading-zero cases and the exact byte representation used for DH transcript hashes and `ZZ` derivation against the reference. See [RSA.cpp:146–180](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/Crypto/RSA.cpp#L146-L180).

### B3. SM encryption, MAC and counters

The IAS channel in this implementation uses two-key 3DES, with `K1,K2,K1`, in CBC mode. The stored key material is 16 bytes, corresponding to the usual 112-bit effective security of two-key 3DES. Each APDU uses an all-zero eight-byte IV. Its `CMAC` class implements a DES retail MAC, not AES-CMAC: DES-CBC under `K1` for preceding blocks and 3DES EDE for the final block. The output is eight bytes. Input padding is ISO/IEC 9797 method 2, `80` followed by zeros to the next eight-byte block, including a new block for already aligned data. See [DES3.cpp](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/Crypto/DES3.cpp), [MAC.cpp:76–129](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/Crypto/MAC.cpp#L76-L129), [padding util.cpp:323–349](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/Util/util.cpp#L323-L349).

Command construction:

- Increment SSC as an unsigned big-endian eight-byte counter before every command and every response. The first protected command after DH therefore uses SSC value 2.
- Set `CLA |= 0C`. Preserve the chaining bit where needed.
- Start MAC input with `pad(SSC || protected_header)`.
- Encrypt padded command data. Even INS uses DO `87` containing `01 || ciphertext`; odd INS uses DO `85` containing ciphertext.
- Encode an expected response length, when present, in DO `97`.
- MAC the padded concatenation of the starting MAC input and the encoded DOs. Append DO `8E` with the eight-byte MAC.
- Send protected data with its outer Lc and `Le=00`, or the extended-length encoding if needed.

For a response, increment SSC again, authenticate encoded DO `85`/`87` plus status DO `99` in their received order, compare DO `8E`, decrypt and remove ISO padding, then return the status from DO `99`. A raw outer `9000` does not mean PIN verification succeeded. See [SM encoder:652–750](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L652-L750) and [response verifier:753–837](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L753-L837).

Transport also matters. The reference splits protected plaintext into chunks of at most `E7` hex, 231 bytes, setting CLA bit `10` on all but the final command. Unprotected command data is split at 255 bytes. It handles outer `61xx` through GET RESPONSE and only then decodes the protected response. There are special paths for `6100` and a source comment about reader/VM chaining failures. Implement and test these paths, not just short successful APDUs. See [response handling and transport:840–1025](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L840-L1025).

The AES in the repository is used for local caching/session secrets. It must not be mistaken for the encryption algorithm of this IAS secure channel.

### B4. DAPP mutual authentication is required

DH alone does not authenticate the chip and does not resist an active MITM. The middleware performs DAPP before sending PIN. The shared terminal CV private key is intentional in the CIE specification; it is not the citizen's private key. The user authenticates with PIN, while the terminal authenticates the real chip using its internal-authentication key. See chip specification §§6.5 and 6.10.3–4 and [DAPP implementation:426–570](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L426-L570).

All commands below are SM-wrapped. Follow the exact BER encoding and transcript byte order in the linked implementation:

1. Construct a terminal CV certificate using the fixed reference terminal RSA key at [IAS.cpp:70–72](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L70-L72) and the shared root private exponent in [ExtAuthKey.cpp](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/ExtAuthKey.cpp). Reference serial `SN_IFD=20 00 00 00 00 00 00 01`; `CHR=00 00 00 00 || SN_IFD`; `CHA=CA_AID || 01`; CPI `8A`; OID bytes `2A 81 22 F4 2A 02 04 01 04`. Build the body as CPI, CAR, CHR, CHA, OID, terminal modulus and exponent concatenated in reference order. Its recoverable RSA block is `6A || recoverable_body || SHA256(full_body) || BC`. The CV outer structure is `7F21{5F37(signature),5F38(nonrecoverable_body_remainder),42(CAR)}`. [IAS.cpp:441–487](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L441-L487).
2. Select external CV verification key with `00 22 81 B6`, data `80 01 41 83 01 84`, logical `Le=00`. Submit the certificate with PSO:VERIFY CERTIFICATE `00 2A 00 AE`, data the CV object.
3. Select the terminal CHR using `00 22 81 A4`, data `TLV(83,CHR)`. GET CHALLENGE `00 84 00 00`, logical `Le=08`, returns `RND_ICC`.
4. Generate a random `PRND` of `terminal_modulus_bytes - 32 - 2` bytes. Compute `H=SHA256(PRND || Y_IFD || SN_IFD || RND_ICC || Y_ICC || g || p || q)`. Perform raw RSA with the terminal private key on `6A || PRND || H || BC`. EXTERNAL AUTHENTICATE `00 82 00 00` receives `SN_IFD || terminal_signature`. [IAS.cpp:489–530](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L489-L530).
5. Select chip internal-authentication key with `00 22 41 A4`, data `84 01 82 80 01 9B`. Generate eight-byte `RND_IFD`. Send INTERNAL AUTHENTICATE `00 88 00 00`, data `RND_IFD`. Response is `SN_ICC[8] || chip_signature`.
6. Recover the chip signature with the RSA public key from `1004`. Require `6A` and `BC` sentinels and compare the embedded 32-byte hash against `SHA256(PRND2 || Y_ICC || SN_ICC || RND_IFD || Y_IFD || g || p || q)`.
7. Replace SSC with `RND_ICC[-4:] || RND_IFD[-4:]` and continue SM. Do not derive different Kenc/Kmac here. [IAS.cpp:534–570](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L534-L570).

For trust, checking a response under an arbitrary key read from the same card is insufficient. Pairing reads SOD and verifies hashes for NIS, internal-authentication keys, DH parameters, serial and certificate. The newer branch also handles SHA-512/RSA-PSS SODs. A production direct implementation must validate the appropriate SOD signer chain to trusted document-signing roots as well as the hashes, and separately validate the citizen authentication-certificate chain. Do not confuse either chain with the public CV terminal key. The exact enrolled-card verification set is in [AbilitaCIE.cpp:239–252,305–327](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/AbilitaCIE.cpp#L305-L327); SOD verification implementations are [IAS.cpp:1339 onward](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L1339). This is an engineering requirement for the proposed port, not a claim that every reference validation path performs a complete trust-anchor check.

### B5. PIN, certificate and signature APDUs

After DAPP, send SM-wrapped `00 20 00 81`, data the full eight ASCII PIN digits. Do not encode BCD, include a NUL terminator or substitute the CAN. On success, read `1003` through SM and parse the X.509 certificate. The official pairing flow does this after `CardAuthenticateEx(FULL_PIN)`. See [VERIFY methods:148–164](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L148-L164), [full PIN construction:475–488](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/AbilitaCIE.cpp#L475-L488), [certificate read:298–303](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/AbilitaCIE.cpp#L298-L303).

| Protected operation status | Meaning evidenced in middleware                     | Agent behavior                                              |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------- |
| `9000`                     | Success                                             | Continue                                                    |
| `63Cx`                     | Wrong PIN/PUK; low nibble `x` is attempts remaining | Display count when available; require a new user submission |
| `6983`                     | Authentication method blocked                       | Stop; offer official PUK recovery workflow                  |
| `6300`                     | Wrong credential without a counter                  | Show an incorrect-PIN error without inventing a count       |
| `6700`                     | Wrong length, mapped to wrong PIN in these wrappers | Treat as an error; do not retry with altered PIN encodings  |

The original card profile permits three PIN attempts and ten PUK attempts. PKCS#11 may hide the exact count even though direct APDUs expose it. See Annex A of the chip specification and [status mapping:497–515](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/AbilitaCIE.cpp#L497-L515). Initial counts on every current card model remain **UNVERIFIED** on hardware.

To sign, the source sends these SM-wrapped logical commands:

```text
MSE:Set AT
00 22 41 A4 06 80 01 02 84 01 81

INTERNAL AUTHENTICATE
00 88 00 00 <Lc> <DigestInfo>
```

The key reference is `81`, algorithm reference `02`. This is not PSO:COMPUTE DIGITAL SIGNATURE `2A 9E 9A`. In fact the original card's authentication-key object forbids Compute Digital Signature and permits Internal Authenticate only after SM + PIN. See [IAS::Sign:122–143](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L122-L143) and chip specification Annex A, p27.

For the backend's SHA-256 digest `d` of the DER CMS signed attributes, supply:

```text
T = 30 31 30 0D 06 09 60 86 48 01 65 03 04 02 01 05 00 04 20 || d[32]
```

The payload is 51 bytes. The card adds the RSA PKCS#1 v1.5 block-type-1 encoding `00 01 FF...FF 00 T` and performs the private-key operation. Do not send the complete modulus-sized padded block. Evidence is the complete source call chain: [CRSA_PKCS1::SignFinal passes the input unchanged, 650–678](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/Mechanism.cpp#L650-L678), [session forwards it, 750–780](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/session.cpp#L750-L780), [template forwards it, 449–473](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L449-L473), and `IAS::Sign` sends it unchanged. The official signing SDK independently [constructs DigestInfo before calling IAS::Sign, CIESigner.cpp:110–143](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie_sign_sdk/src/CIESigner.cpp#L110-L143).

The original IAS key object is 256 bytes, RSA-2048, so the expected signature is 256 bytes. Read and check the actual certificate modulus rather than hardcoding that size. Raw output here means the RSA signature octets, without CMS or PDF packaging; it does not mean unpadded textbook RSA. The source chain establishes the padding boundary; a hardware test of the resulting signature remains **UNVERIFIED** in this research.

The backend must hash the DER SET OF signed attributes, with the CMS signing rules for its tag, not the PDF digest a second time. There are two hashes in a normal CMS-with-attributes flow: the PDF ByteRange hash stored in `messageDigest`, and the hash of the DER signed attributes given to RSA. See [RFC 5652 §5.4](https://www.rfc-editor.org/rfc/rfc5652#section-5.4) and [RFC 8017 §9.2](https://www.rfc-editor.org/rfc/rfc8017#section-9.2).

### B6. PUK and reset retry counter

Within a fresh DH + DAPP session, verify the eight ASCII PUK digits with `00 20 00 82`. The source provides two related reset paths:

- `00 2C 03 81`, no data, resets the PIN retry counter after PUK verification. A subsequent `00 2C 02 81`, data the new full PIN, sets the PIN in the PKCS#11 `C_InitPIN` path.
- The desktop `UnlockPIN` helper verifies PUK and directly sends `00 2C 02 81` with the new full PIN, then updates the encrypted first-four-digit cache if enrolled.

Normal PIN change is `00 24 00 81`, data `oldPIN[8] || newPIN[8]`. All are SM-wrapped. See [IAS.cpp:167–193](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/IAS.cpp#L167-L193), [PKCS#11 initialization:478–509](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/PKCS11/CIEP11Template.cpp#L478-L509), [desktop UnlockPIN:338–392](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/CSP/PINManager.cpp#L338-L392).

PUK recovery need not be part of the first agent release. It changes card state and risks exhausting a non-resettable PUK counter; the signing UI can direct the user to the official application. No reset/unblock command was executed for this report.

## C. OpenSC and alternative stacks

### C1. OpenSC generation support

Working CIE 3.0 signing through OpenSC's own driver is **UNVERIFIED**, and the available evidence points against treating it as supported. The [CIE 3.0 support request #2486](https://github.com/OpenSC/OpenSC/issues/2486) is closed as not planned. Its suggestion to start from IAS-ECC is not an implementation.

Current OpenSC [`card-itacns.c`](https://github.com/OpenSC/OpenSC/blob/fc27ee8768cb882fceb99535dce8b6a966534dcb/src/libopensc/card-itacns.c#L53-L130) recognizes CIE V1/V2. [`cards.h`](https://github.com/OpenSC/OpenSC/blob/fc27ee8768cb882fceb99535dce8b6a966534dcb/src/libopensc/cards.h) and [`card-cardos.c`](https://github.com/OpenSC/OpenSC/blob/fc27ee8768cb882fceb99535dce8b6a966534dcb/src/libopensc/card-cardos.c) likewise contain old-generation CIE identifiers. [`card-iasecc.c`](https://github.com/OpenSC/OpenSC/blob/fc27ee8768cb882fceb99535dce8b6a966534dcb/src/libopensc/card-iasecc.c) does not establish a CIE 3.0 DH/DAPP implementation. CardOS, IAS-ECC and CIE are not interchangeable driver names.

OpenSC's `pkcs11-tool` is a separate matter. It can be used as a PKCS#11 client against `CIEPKI.dll`/`libcie-pkcs11.*`, even when `opensc-pkcs11` cannot drive the card. A successful command using the official `--module` would not prove OpenSC CIE 3.0 driver support.

## D. Signature status, validation and association minutes

### D1. FEA, formats and profiles

The Ministry classifies [Firma con CIE](https://www.cartaidentita.interno.gov.it/info-utili/firma-con-cie/) as firma elettronica avanzata, FEA. It documents PAdES for PDFs and CAdES for other files, with physical card possession and PIN. This does not establish FEQ/QES or the statutory Italian qualified form called firma digitale. PAdES is a format, not a qualification level.

The [integration page](https://www.cartaidentita.interno.gov.it/pa-e-imprese/integra-firma-con-cie-ciesign/) confirms PAdES with or without graphical appearance, CAdES `.p7m`, and desktop implementations for Windows/macOS/Linux. A drawn signature image is optional appearance; the RSA/CMS signature supplies the integrity check.

The official source sets `DISIGON_OPT_CADES=1` and, for PDFs, selects `DISIGON_PDF_SUBFILTER_ETSI_CADES` in [CIESign.cpp:40–65](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie-pkcs11/Sign/CIESign.cpp#L40-L65). The SDK includes a `SigningCertificateV2` attribute in [SignerInfoGenerator.cpp](https://github.com/italia/cie-middleware-linux/blob/a05337fc3ea3a526e6f173634c0f5ed0eb059859/cie_sign_sdk/src/SignerInfoGenerator.cpp). These support a CAdES-based PDF signature design. Exact **PAdES-BES/CAdES-BES or current baseline profile conformance of each distributed package is UNVERIFIED** without sample output and a conformance validator. Do not silently equate historical BES terminology with a tested PAdES-B-B, B-T or LT/LTA result. No default timestamp or long-term validation guarantee was established.

### D2. Certificate profile and validator consequences

The official [chip specification §6.12.2, p20](https://www.cartaidentita.interno.gov.it/downloads/2021/03/cie_3.0_-_specifiche_chip.pdf#page=20) specifies:

- Critical key usage `digitalSignature`, bit 0, with no other usage bits. Therefore `nonRepudiation`, also called `contentCommitment`, is not set.
- Noncritical extended key usage containing only TLS client authentication, `id-kp-clientAuth`, OID `1.3.6.1.5.5.7.3.2`.
- A DER X.509 authentication certificate, with the document's validity and issuer information. The original certificate signature algorithm is SHA256-with-RSA.

This is the authentication certificate used by the official FEA design, not evidence of a separate qualified document-signing certificate. Absence of `contentCommitment` does not alone answer the legal FEA question. Conversely, correct RSA verification does not establish qualification.

A practical inference is that validators requiring qualified trust-list status, a contentCommitment bit or a document-signing EKU may reject or downgrade CIE output. Configure a documented CIE-aware validation policy without changing certificate extensions or presenting the result as QES. Inspect the actual end-entity certificate on first integration; current-card conformity to every historical profile detail is **UNVERIFIED** without a card sample.

### D4. Constraints for PoliNetwork's verbali

The Ministry describes broad FEA use subject to exclusions. [CAD art.21(2-bis), official consolidated text](https://www.gazzettaufficiale.it/atto/serie_generale/caricaArticolo?art.codiceRedazionale=005G0104&art.dataPubblicazioneGazzetta=2005-05-16&art.flagTipoArticolo=0&art.idArticolo=21&art.idGruppo=4&art.idSottoArticolo=1&art.idSottoArticolo1=10&art.progressivo=0&art.versione=6) requires, except for authenticated execution, qualified/digital signatures for electronic private deeds covered by civil-code art.1350 points 1–12. Ordinary internal association minutes do not automatically fall into those categories. Suitability for PoliNetwork's actual documents is nevertheless **UNVERIFIED** without its bylaws, the act recorded and any receiving authority's requirements.

There is a narrower legal question than the cryptography alone answers:

- [DPCM 22 February 2013 art.60](https://www.gazzettaufficiale.it/atto/serie_generale/caricaArticolo?art.codiceRedazionale=13A04284&art.dataPubblicazioneGazzetta=2013-05-21&art.flagTipoArticolo=0&art.idArticolo=60&art.idGruppo=5&art.idSottoArticolo=1&art.idSottoArticolo1=10&art.progressivo=0&art.versione=1) limits ordinary FEA solutions to the legal relationship between signer and solution provider.
- [Art.61(2)](https://www.gazzettaufficiale.it/atto/serie_generale/caricaArticolo?art.codiceRedazionale=13A04284&art.dataPubblicazioneGazzetta=2013-05-21&art.flagTipoArticolo=0&art.idArticolo=61&art.idGruppo=5&art.idSottoArticolo=1&art.idSottoArticolo1=10&art.progressivo=0&art.versione=1) expressly addresses CIE replacing FEA towards public administrations for CAD arts.64–65 activities.
- [Art.57](https://www.gazzettaufficiale.it/atto/serie_generale/caricaArticolo?art.codiceRedazionale=13A04284&art.dataPubblicazioneGazzetta=2013-05-21&art.flagTipoArticolo=0&art.idArticolo=57&art.idGruppo=5&art.idSottoArticolo=1&art.idSottoArticolo1=10&art.progressivo=0&art.versione=1) includes identification/acceptance, evidence retention and insurance duties for the providers it covers; paragraph 6 exempts the art.61(1)–(2) solutions.

The Ministry's broad product guidance does not by itself establish that a custom private association service inherits every art.57 exemption. Whether PoliNetwork's deployment is within those rules, and which duties apply, needs a legal determination. This is not a finding that internal CIE-signed minutes are prohibited.

For implementation, record the signer's identity and role, the exact frozen document, explicit approval, completed signature and validation results. Retention and any preservation system must be chosen for the document category, not inferred from PDF format. These are practical evidence-design recommendations.

External filing is a separate acceptance question. For example, the Ministry of Labour's [RUNTS technical annex updated 31 March 2026](https://www.lavoro.gov.it/sites/default/files/documenti-pubblicita-legale/Decreto%20Direttoriale%20n.%2036%20del%2031%20marzo%202026%20unito.pdf) specifies digital signatures for certain conformity declarations and describes CAdES/P7M or permitted portal methods. A CIE FEA document is not automatically accepted everywhere that requests firma digitale. Verify the exact destination and document type before committing to FEA as the sole option.

## E. Recommendation for the Go agent

### Primary implementation

Use official PKCS#11 through a native worker, loaded with `dlopen` on Unix-like systems and the Windows loader on Windows. Keep a narrow Go-facing interface such as `ListSigners`, `GetCertificate` and `SignSHA256Digest`. A worker process contains middleware crashes and allows an x86_64 module on Apple Silicon to run with an x86_64 worker. An arm64 process cannot load an x86_64 dylib. Architecture evidence and unresolved binary questions are listed in A1 and A6. In particular, macOS cache discovery from an unsandboxed worker must be qualified before relying on that combination.

The signing contract should be explicit:

```text
Input: chosen certificate fingerprint + SHA-256 digest of DER CMS signed attributes
       + user-entered PIN suffix for a paired official token
Output: RSA PKCS#1 v1.5 signature bytes + same certificate fingerprint

C_Initialize
C_GetSlotList(tokenPresent=true)
C_OpenSession(CKF_SERIAL_SESSION)
C_FindObjects(CKO_CERTIFICATE) -> CKA_VALUE; select matching certificate
C_Login(CKU_USER, last_four_PIN_digits)
C_FindObjects(CKO_PRIVATE_KEY, matching CKA_ID)
C_SignInit(CKM_RSA_PKCS, private_key)
C_Sign(SHA256_DigestInfo_prefix || digest)
C_Logout; C_CloseSession
```

Resolve handles again after removal/reinsertion. Enumerate readers and certificate identities rather than choosing slot zero or a fixed label. Accept only a 32-byte SHA-256 digest at this API boundary; construct DigestInfo locally. Verify the output with the certificate's RSA public key before returning it. The backend must verify again and reject a different certificate, changed PDF revision, wrong digest or reused/cancelled transaction. These are implementation recommendations derived from the source behavior, not features the middleware adds for the web dashboard.

Pairing is a setup step in the official application on each computer and relevant user account. Do not pass an eight-digit PIN to the paired-token `C_Login` path or automatically try both lengths. Do not store the PIN suffix in the agent. The middleware itself retains a session PIN representation and re-verifies the full PIN inside signing, so a failed transport is not grounds for silently repeating authentication. Exact retry counts are not portable through PKCS#11.

Keep the backend responsible for PDF/CMS construction, chain validation, revocation, timestamps and archival policy, as already chosen. The local endpoint must accept only authorized, short-lived signing transactions from the configured dashboard, with local user consent. The current architecture passes a digest, so the agent cannot independently establish that it corresponds to the PDF the browser displayed. Bind the backend transaction to the frozen document revision and signer, and record the approval as part of the signing evidence. This follows from the chosen digest-only design.

### Fallback and practical escape routes

1. If loading fails, first diagnose distribution path, process architecture, reader service and pairing. A different path or Intel worker is much cheaper than reimplementing IAS.
2. If official PKCS#11 fails on an otherwise supported setup, offer a separately qualified alternative implementation behind the same signer interface. OpenCIE-PKCS11 is relevant, but its maturity, licensing and own pairing/cache behavior need review before shipping it. It is a potential provider, not proof that a Go binding eliminates native dependencies.
3. Develop a direct Go PC/SC provider only as an opt-in fallback. It can accept all eight PIN digits and avoid the official disk pairing cache. It must implement DH, retail MAC, DAPP, SOD trust, card variants and transport state exactly, with hardware tests. A digest signer is small; a correct CIE protocol stack is not.
4. Until that fallback is qualified, an official desktop signing workflow with manual upload is a product fallback. It does not implement the selected raw-signature architecture and should not be described as equivalent automation.

The strongest reason for official PKCS#11 is maintaining compatibility with issued cards without owning the whole IAS implementation. Its main risks are installation/pairing, stale or architecture-specific binaries, hidden retries and source defects. Direct PC/SC removes a deployment dependency but transfers the protocol, cryptography, trust and reader compatibility burden to PoliNetwork.

### Required qualification before deployment

These tests remain **UNVERIFIED** and are the minimum useful next experiment:

- On Windows x64, macOS Intel/Apple Silicon and the chosen Linux distributions, identify the installed binary and architecture, enumerate slots, read the paired public certificate without login, sign once using explicit SHA-256 DigestInfo, and verify using an independent RSA implementation.
- Repeat across older Gemalto/STM and newer NXP/Actalis/Bit4id cards. Record exact model, ATR, middleware version and reader model. Keep invalid-PIN testing deliberate and limited; never consume retries automatically.
- Exercise unpaired cards, missing cache, PIN changes through the official app, card removal between certificate selection and signing, lock contention with browser authentication, worker crashes and cancellation. Confirm that cancellation does not cause another PIN attempt or a duplicate signature request.
- Validate the assembled PDF with a CIE-aware policy using the correct CIE authentication roots and revocation data. Report cryptographic validity, FEA classification and qualified status separately. Test long-term validation/timestamp behavior according to the association's retention requirements.
